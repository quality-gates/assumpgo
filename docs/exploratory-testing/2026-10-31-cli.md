# Exploratory testing: assumpgo CLI (2026-10-31)

The pass exercised the public CLI at commit `9fd4b2c` (v0.1.10), on Linux amd64 with Go 1.26.8. The binary, Go caches, module cache, and fixtures lived in a disposable directory inside the worktree. The module has no external dependencies and the build used `GOFLAGS=-mod=readonly`.

The [replay script](2026-10-31-cli/replay.sh) requires Bash, Python 3, Go, and hard-link support. It recreates the fixtures and removes them on exit. The [first run](2026-10-31-cli/replay-output.txt) and [second run](2026-10-31-cli/replay-output-2.txt) produced identical output. No server, browser, container, or background process was started by the replay.

## Journeys

1. **Gate Go code.** The user expects assertions to pass and assumptions to fail the gate. The fixture combined a package constant, strict equality, a bare variable, a negative comparison, and a comma-ok guard. The CLI reported only the bare variable and negative comparison and exited 110. A clean equality-only file exited 0. The bundled `dog.go` smoke test reported one finding and exited 110.
2. **Select targets and exclusions.** The user expects `./...` to find included Go files while skipping `testdata`. The scan reported three findings across the root and a subdirectory. Excluding the subdirectory removed its finding. A hard link supplied alongside its target did not duplicate findings. A custom build-tag variation exposed the false clean result below.
3. **Produce a CI report without damaging source.** The user expects checkstyle XML in the requested file and protection against overwriting an input. Python parsed the report and found one file and two errors. An output path hard-linked to the input was refused with exit 100, and a byte comparison confirmed that the source remained unchanged. Uppercase `XML` was rejected with exit 100, as documented.

## Confirmed bug

[Issue #135](https://github.com/quality-gates/assumpgo/issues/135) records the custom build-tag false clean, with `bug` and `needs-triage` labels. A CI job using `GOFLAGS=-tags=special` can miss assumptions in files included by that build.

Starting with a clean untagged file and a tagged file containing `if ready {`, `GOFLAGS=-tags=special go list -f '{{.GoFiles}}' ./tagged` included both files. `GOFLAGS=-tags=special assumpgo ./tagged` reported zero assumptions and exited 0. Directly targeting the tagged file reported the assumption and exited 110. Both recreated runs agreed. The directory-walk documentation says it matches Go's build constraints. The constant-resolution documentation specifically names build tags as part of the current build context. Neither explicitly promises support for `GOFLAGS`.

[Issue #104](https://github.com/quality-gates/assumpgo/issues/104) covered default build constraints. [Issue #124](https://github.com/quality-gates/assumpgo/issues/124) explicitly left custom tags out of its refactor. Neither issue rejected the configured-build case. The [2026-09-26 report](2026-09-26-cli.md) noted that the CLI has no `-tags` flag and did not test extra tags.

## Other observations and limits

No other candidate was confirmed or left unresolved in these journeys. Windows paths, other operating systems, non-UTF-8 paths, and external CI integrations were not exercised. The local single-worker mutation gate timed out after 20 minutes; tracked source files were restored. Build, unit tests, vet, formatting, gocyclo, and ineffassign passed. The XML check used Python's standard library rather than an external CI parser. The output file was parsed after the CLI exited, not merely checked for a success message.

The explicit file path provides a workaround for a small number of tagged files, but it does not make the documented recursive scan reflect `GOFLAGS`. The report describes observations only and does not propose a product fix.
